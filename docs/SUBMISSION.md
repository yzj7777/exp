# 需求翻译官｜创意阶段提交材料（草稿）

> **状态：** 创意阶段材料工作稿，提交前必须按官方最新通知核实字数、字段、模板和截止时间。技术描述只对应当前实际原型：本地规则驱动，未接入大语言模型或 openJiuwen / WorkSwarm。

## 作品名称

**需求翻译官：把模糊想法变成可确认、可验收的需求**

## 项目简介

需求沟通常从“做得方便一点”“提高会议效率”等模糊想法开始。需求方、产品和研发人员需要反复确认用户是谁、问题发生在哪里、功能边界是什么，以及怎样判断需求真正完成。需求翻译官面向需求提出者与产品/研发团队，通过场景化的交互访谈收集目标用户、痛点、预期结果、关键流程、范围约束和验收标准，并把未确定内容单独标注，生成可供需求评审的结构化草稿。

本项目的设计原则是“先澄清，再整理；不确定就标记，不替用户做决定”。当前比赛原型采用浏览器端规则驱动：根据关键词识别会议协作、订单查询、研发工具、科研工作等场景，调整提问顺序和措辞；对笼统回答最多追加一次针对性追问。项目无需 API 密钥即可体验，当前不调用大语言模型，也未集成 WorkSwarm。后续可在核实赛事要求和技术资源后，评估模型或 openJiuwen 生态集成。

## 应用场景说明

**首版重点场景：产品功能需求澄清。**

例如，业务人员提出“想让团队会议协作更高效”。需求翻译官先确认谁是主要使用者，再了解问题发生在会前、会中还是会后，追问希望改变的结果、典型流程、系统或权限约束，以及判断效果的方式。若用户只说“提高效率”，系统会继续请求具体例子。最终输出需求摘要、用户与场景、痛点、预期结果、功能需求初稿、范围约束、验收标准草稿和待确认事项。

**目标用户：** 不熟悉需求文档写法的业务人员或客户、负责需求访谈的产品/项目人员，以及需要明确开发边界和验收条件的研发团队。

**核心痛点：** 信息散落在口头沟通中；模糊词语无法直接验收；未确认的假设容易被误当作正式需求；团队在开发前后反复澄清。

## 创意特点

1. **从需求澄清出发，而不是直接扩写。** 先围绕关键要素提问，再生成文档，避免一句模糊输入直接变成一份看似完整但包含大量假设的方案。
2. **场景驱动的访谈。** 当前原型依据场景规则调整问题顺序和表达；笼统回答会触发一次进一步澄清。
3. **显式呈现不确定性。** 待确认回答、额外补充与 Agent 写法建议不会伪装成已确认需求；用户可跳过问题、修改已录入字段，草稿会标注来源与确认状态。
4. **轻量、可体验。** 浏览器即可运行，不需要配置 API 密钥或连接业务数据。

## 技术方案

当前 Demo 由原生 HTML、CSS 和 JavaScript 实现。`web/agent-core.js` 使用本地关键词规则进行场景分类、访谈顺序选择、领域问题生成、含糊回答判断和补充信息字段归类；`web/app.js` 管理当前会话状态与交互；文档由前端模板生成 Markdown，支持复制或下载。当前无服务端、无模型 API、无外部数据源，访谈内容仅保留在当前浏览器页面会话中，刷新后清空。

**当前技术边界：** 关键词规则可能误分类，不能替代开放式语义理解、复杂冲突检测或专业评审；生成结果需由用户确认。项目材料不宣称已使用未集成的模型或开源生态组件。

## DEMO 与展示方式

首选以交互式展示网页呈现项目：先说明目标用户与痛点，再通过场景标签展示问题变化，最后在内嵌可操作 Demo 中现场完成一次需求访谈并查看 Markdown 草稿。展示页同时公开当前规则驱动架构、能力边界和待验证的评测计划。当前未接入大语言模型或 WorkSwarm。

当前展示方式包括交互式项目网页和可操作 Demo；另已按参赛者提供的 7 页模板 PDF 重制项目介绍 PPT。第 2–4 页为原生可编辑内容，第 1 页使用模板封面图作为底图，第 5–7 页保留模板 PDF 页面图像；尚未取得可核验的原生官方 `.pptx` 母版。预录演示视频暂不制作，除非官方提交入口明确要求。登录提交入口后仍需核实网页链接、PPTX/PDF 和视频的必交形式；若要求原生模板再迁移。
