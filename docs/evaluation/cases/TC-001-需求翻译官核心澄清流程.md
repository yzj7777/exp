# TC-001｜需求翻译官核心澄清流程

## 测试记录

- **类型：** 端到端对话桌面推演（LLM + Agent 角色模拟）
- **测试目的：** 检验 Agent 是否能通过追问把模糊产品想法整理成结构化、可确认的需求草稿。
- **初始想法来源：** 参赛者真实提出的“需求翻译官通过交互式问答把模糊需求具体化”。
- **回答来源：** 下文“模拟用户”回答由本次测试为覆盖需求要素而构造，**不是参赛者或真实客户的实际回答，不构成用户研究证据**。
- **运行方式：** 由大语言模型在本次对话中扮演需求访谈 Agent；没有调用外部模型 API，也没有将模型接入网页产品。
- **通过原则：** 不把模拟补充内容冒充真实输入；每个要点保留来源状态；模糊关键回答需追问；最终草稿可回溯到访谈回答。

## 输入

> 我想做一个叫“需求翻译官”的 Agent，能通过反复沟通、交互式问答，把模糊的需求具体化。

### 测试预期

- 识别到产品是交互式需求澄清 Agent；
- 不擅自假定目标用户、功能范围或成功指标；
- 至少澄清目标用户、痛点、期望结果、交互流程、范围约束和验收方式；
- 对“说清楚”“更好用”等不够可验证的回答继续追问；
- 输出中区分已确认、建议和未决项。

## 完整访谈记录

### 第 1 轮：目标用户

**Agent：** 谁会最常使用需求翻译官？请说一个具体角色，以及他在什么情况下会打开它。

**模拟用户：** 主要是业务部门提出软件功能需求的人，以及负责整理需求的产品经理。业务方只知道自己想解决什么问题，不太会写需求文档。

**Agent 状态更新：** 目标用户候选为业务需求提出者和产品经理；来源为本测试中的模拟回答，待真实项目负责人确认。

### 第 2 轮：当前痛点

**Agent：** 现在从提出想法到形成产品需求，最容易卡在哪里？能描述一个典型例子吗？

**模拟用户：** 业务方可能只说“做一个更好用的审批”。产品经理需要来回问使用者是谁、什么时候审批、退回后怎么办，沟通几轮后才知道真正需要解决的流程问题。

**Agent 状态更新：** 痛点候选为初始描述过于笼统，关键流程与异常情况需要反复补问；仍为模拟资料。

### 第 3 轮：预期结果

**Agent：** 如果这个 Agent 有帮助，用户最终应该拿到什么？

**模拟用户：** 希望拿到一份结构化需求草稿，至少包含用户、场景、问题、目标、功能范围、边界和验收方式。用户需要能检查和修改，而不是直接把 AI 写的内容当结论。

**Agent 状态更新：** 预期产物是可编辑、待用户确认的需求草稿；“至少包含”的字段作为本次模拟用户确认项。

### 第 4 轮：关键交互流程

**Agent：** 用户输入第一句话之后，Agent 应如何进行访谈？

**模拟用户：** 先识别缺了什么信息，再每次问一两个关键问题。用户答得含糊时举例或继续追问。回答后更新一份摘要，结束前让用户确认。

**Agent：** 你说的“关键问题”应按什么优先级？

**模拟用户：** 先问会影响目标、用户、范围或验收的问题；不重要的细节可以先放进待确认项，不要连续问很多题。

**Agent 状态更新：** 访谈采用优先级驱动的少量追问，并支持阶段性摘要和用户确认；“每次一两个问题”是本模拟案例要求，仍须产品负责人确认是否作为实际交互规则。

### 第 5 轮：范围与约束

**Agent：** 第一版要支持哪些需求类型？有哪些明确不做的事或数据限制？

**模拟用户：** 先支持软件产品功能需求。第一版不自动做技术选型、不估算工期，也不替用户拍板。访谈信息默认只在当前会话里使用，用户要自己确认后才能导出。

**Agent 状态更新：** 首版领域、非目标和会话数据处理要求均由模拟用户提出；需要真实项目负责人确认，不能当作原始想法中已确定内容。

### 第 6 轮：成功标准

**Agent：** 怎么判断一份需求“具体化”了？

**模拟用户：** 需求文档包含必要字段，评审人能看懂。

**Agent 识别：** “必要字段”和“看懂”还不能直接检验。建议进一步定义字段清单及评审办法。

**Agent：** 哪些字段必须在输出里？由谁用什么方式判断“看懂”？

**模拟用户：** 目标用户、场景、痛点、目标、主流程、范围外内容、未决问题和验收标准必须有；不知道的要标待确认。先由提出需求的人确认是否准确，再由产品经理判断是否足以进入需求评审。

**Agent 状态更新：** 得到可检查的字段清单及两阶段人工确认标准。尚未定义“足以进入评审”的统一评分细则，所以该项仍需后续制定。

### 第 7 轮：草稿确认

**Agent 摘要：** 当前草稿的目标用户是业务需求提出者和产品经理；问题是初始想法缺少关键上下文，导致产品经理反复澄清；Agent 应优先询问影响目标、用户、范围、验收的问题，并把无法确认的信息标成待确认；输出需求草稿供提出者核对，再由产品经理判断能否进入评审。以上具体用户和流程来自模拟回答，不是已验证事实。是否准确？

**模拟用户：** 对本测试案例来说准确。实际项目里还需要真实用户确认。

## 本案例生成的需求草稿

> **状态：** 基于本次角色模拟，不是正式产品规格。原始项目想法由参赛者提出；其余细化回答为模拟用户补充。进入开发前必须由项目负责人和目标用户重新确认。

### 项目概述

需求翻译官是一款面向软件产品需求澄清的交互式 Agent 原型。用户用自然语言描述初步想法，Agent 通过少量、按优先级排列的问题补齐上下文，记录用户回答与未决事项，最后形成可修改、可确认的需求草稿。

### 目标用户与场景（模拟确认，待真实确认）

- **业务需求提出者：** 知道要解决的问题，但不熟悉结构化需求表达。
- **产品经理：** 需要访谈需求方、识别缺口并整理评审材料。
- **触发场景：** 一条初始需求表述过于宽泛，需要在正式需求评审前澄清。

### 痛点（模拟确认，待真实确认）

初始需求经常缺少用户角色、触发场景、主流程、异常处理或验收办法，产品经理需通过多轮人工沟通补齐信息，需求范围也容易被误解。

### 功能需求（本案例模拟确认）

1. 允许用户用自然语言输入初始需求。
2. 识别当前需求中尚未明确的关键要素，并优先询问影响目标、用户、范围或验收的问题。
3. 每轮控制问题数量，避免一次性抛出长问卷。
4. 对含糊回答继续追问；用户无法回答时允许记录为待确认。
5. 维护访谈摘要，区分用户回答、Agent 建议和待确认事项。
6. 访谈结束前展示总结，允许需求提出者核对和修改。
7. 输出结构化草稿，供产品经理判断是否进入需求评审。

### 草稿必备字段（本案例模拟确认）

- 目标用户；
- 使用场景；
- 当前痛点；
- 预期目标；
- 主流程；
- 范围内与范围外事项；
- 未决问题；
- 验收标准。

无法从回答中得出的字段必须标记为“待确认”，不得自动编造。

### 范围外（本案例模拟确认）

- 不自动决定技术架构或产品取舍；
- 不自动估算工期与成本；
- 不把 AI 建议当作需求方确认；
- 不直接替代产品经理审批或需求评审。

### 验收标准（本案例模拟确认）

1. 用户可输入一条自然语言需求并完成一轮多轮澄清。
2. 生成文档包含上列 8 项字段；缺失信息显式标为“待确认”。
3. 草稿里的每个已确定事实都能追溯到本轮用户回答；没有依据的断言数量为 0。
4. 需求提出者可以检查并纠正摘要；纠正后草稿同步更新。
5. 产品经理可基于草稿判断是否具备进入需求评审的最低信息。**本条的“最低信息”判定规则尚未定义，是未决事项。**

### 待确认事项

- 目标用户、场景和痛点尚未通过真实访谈验证；
- “少量问题”每轮具体上限需产品负责人确认；
- 需求草稿的文件格式、保存时长、隐私与部署方式需确认；
- 需求评审准入标准和量化效果指标尚未确定；
- 第一版是否只针对软件功能需求需产品负责人确认。

## 测试结果与评分

| 检查项 | 结果 | 证据 |
|---|---|---|
| 识别目标用户、痛点、目标、流程、边界、验收 | 通过（6/6） | 访谈第 1–6 轮均覆盖了对应要素；这些答案是模拟输入。 |
| 对笼统答案追加澄清 | 通过（1/1） | 第 6 轮对“评审人能看懂”追问字段清单和确认角色。 |
| 明确事实来源与状态 | 通过（桌面检查） | 输出将参赛者原始想法与模拟补充分开，并列出待确认项。 |
| 无依据内容伪装为真实用户事实 | 通过（桌面检查） | 文档多处标注“模拟确认、待真实确认”，没有声称外部访谈。 |
| 交互代码端到端已自动化验证 | 未测试 | 本案例由大语言模型在对话中完成推演，不是网页自动化测试。 |

**本测试判定：** 对桌面推演用例通过；不等于产品功能验收通过，也不能据此宣称真实用户有效。下一步应将同一对话路径放入网页 Agent，并由目标用户真实试用后复测。
