# 需求翻译官｜评测方案与初步结果

## 1. 评测目标

验证当前**规则驱动原型**是否能：

1. 对常见输入选对访谈场景；
2. 为场景选择合理的问题顺序和措辞；
3. 对笼统或不确定回答进行澄清；
4. 将补充内容合理归档并标成待确认；
5. 生成与用户回答一致、不会把猜测伪装成事实的草稿。

这不是大语言模型能力评测；当前产品没有接入 LLM，也不声称实现复杂语义理解。

## 2. 测试资产

- 分类样例：`tests/evaluation-cases.json`，25 条人工编写的规则测试样例，覆盖会议协作、订单查询、研发工具、科研工作和通用需求，每类 5 条。
- 规则单测：`tests/agent-core.test.js`。
- 可复现评测命令：`node tests/evaluate-agent.js`。
- 用户原始想法需求草稿：`docs/examples/需求翻译官-用户原始想法需求草稿.md`。这是项目提出者真实表达整理的草稿，不是外部客户需求，也不是用户研究证据。

## 4. 已完成的端到端桌面推演

完成案例：`docs/evaluation/cases/TC-001-需求翻译官核心澄清流程.md`。本案例以参赛者真实初始想法为输入，由大语言模型在对话中扮演 Agent，并使用清楚标注的模拟回答覆盖目标用户、痛点、目标、流程、范围和验收标准；完成追问、总结、草稿及逐项检查。

桌面推演检查结果：关键要素 6/6；笼统回答追问 1/1；来源与待确认项人工审核通过。**它不是网页自动化测试、不是实际 API 调用，也不是外部用户访谈。**模拟用户回答只用于完整走通方案，不是参赛者确认的新产品需求。

## 5. 下一阶段真实体验评测协议（待开展）

### 参与者与任务

- 邀请至少 5 位非本项目开发者，最好包含需求提出者、产品/项目人员和研发人员。
- 每位参与者使用自己熟悉的一个真实但不含敏感资料的需求；需取得同意，不收集公司机密、个人敏感数据或未授权内容。
- 先独立写一份需求摘要，再用需求翻译官完成访谈；顺序在参与者间交替，减少顺序偏差。
- 结束后请参与者核对生成文档，并让一位不参与开发的评审者盲评文档。

### 记录指标

1. 访谈完成率与总耗时；
2. 关键要素覆盖率：目标用户、痛点、目标、流程、范围/限制、验收标准（6 项）；
3. 未确认事实误标为确定的数量（目标为 0）；
4. 澄清问题相关性（1–5 分）；
5. 文档可理解性、可执行性和用户满意度（各 1–5 分）；
6. 需求提出者与盲评者指出的重大遗漏或错误数；
7. 与参与者原始摘要相比，是否减少歧义，不能只比较字数。

### 评分与通过门槛（预设，不是已测结果）

- 未确认信息被伪装成事实：必须为 0；
- 6 项关键要素覆盖率：参与者确认后平均至少 4/6；
- 问题相关性、文档可理解性：平均至少 4/5；
- 重大错误：不得出现将用户意图反向改写、权限或约束严重误述等情况；
- 完成访谈时间：记录基线，不预设效率提升百分比；应比较参与者的体验和文档质量后再得出结论。

### 研究诚信

- 公开样例测试、参与者评测和线上运行日志必须分开报告。
- 未实际开展的测试不能填为已完成；无参与者授权，不发布原始访谈文本。
- 如果样本未达到上述数量，报告实际 N 值，并标注为探索性可用性测试。

## 6. 已知失效模式与后续改进

- 关键词同义表达、拼写错误、跨领域复合输入可能导致错分；下一轮应增加难例和混合场景样例。
- 自由文本短语启发式可能把简短但明确的回答当作含糊回答。
- 单次澄清不一定足以把需求说清；评测需记录过度追问与追问不足。
- 补充内容归档靠关键词匹配，可能误分类；应在草稿中让用户显式确认归属。
- 当前固定要素覆盖不等于真实的动态需求规划；需在后续模型或更完善的状态策略实现后另做独立评估。
